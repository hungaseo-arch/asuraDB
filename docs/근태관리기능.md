# 근태 관리 기능

지오펜싱(GPS 반경) 기반 출퇴근 기록과 휴가·초과근무 승인을 다루는 기능이다.
**관리자용 3개 화면(AsuraDB 대시보드)** 과 **직원용 PWA(별도 앱)** 두 축으로 나뉜다.

> 최초 도입 2026-09-02. 변경 시 [`웹사이트_운영_변경이력.md`](웹사이트_운영_변경이력.md) 에 기록한다.

---

## 1. 전체 구성

| 구분 | 위치 | 쓰는 사람 | 하는 일 |
|---|---|---|---|
| 출퇴근 — 근태현황 | `/attendance` | 관리자 | 당일 출퇴근 현황, 지오펜싱 근무지 등록·수정 |
| 휴가 — 휴가·초과근무 | `/leave-management` | 관리자 | 휴가·연차·초과근무 신청 승인/거절 |
| 보고서 — 근태집계 | `/attendance-report` | 관리자 | 일자별 출근/미출근 집계, CSV 내려받기 |
| 직원용 PWA | `employee-pwa/` (별도 프로젝트) | 전 직원 | 휴대폰에서 GPS 로 출퇴근 체크, 휴가 신청, 내 기록 조회 |

관리자 3개 화면은 사이드바 **「근태」** 그룹에 있고, 라우터 역할 게이팅상
`super_admin`·`staff` 만 접근된다(`distributor`·`end_user` 는 `/quote` 로 리다이렉트).

## 2. 관리자 화면

### 2.1 출퇴근 — 근태현황 (`/attendance`)

- **상단 카드 4개** — 전체 직원 / 오늘 출근 / 지오펜싱 내 / 미출근
- **지오펜싱 영역 목록** — 근무지를 추가·수정·삭제한다. 하나의 근무지는
  `이름 + 위도 + 경도 + 반경(m)` 으로 정의된다.
  삭제는 실제 삭제가 아니라 `is_active = false` 비활성화라 과거 기록이 깨지지 않는다.
- **오늘 출퇴근 기록 표** — 직원·부서·출퇴근 구분·시각·지오펜싱 판정·본사에서의 거리

> 기록 표는 **오늘 날짜 기준**이다. 과거 날짜는 근태 보고서에서 본다.

### 2.2 휴가 — 휴가·초과근무 (`/leave-management`)

- **탭 2개** — 휴가/연차, 초과근무
- **상태 필터** — 전체 / 대기 / 승인 / 거절
- **승인·거절 버튼** — `status = 'pending'` 인 건에만 나타난다.
  누르면 `status`, `approved_by`, `approved_at` 이 한 번에 기록된다.
- 휴가 종류: 연차(`annual`) · 병가(`sick`) · 개인사유(`personal`) · 기타(`other`)

> **승인자 지정 방식** — 화면이 `employees.position = 'admin'` 인 직원을 찾아 승인자로 넣는다.
> 그런 직원이 없으면 "관리자 정보를 찾을 수 없습니다" 로 승인이 막힌다.
> 현재는 총괄 1명의 position 을 `admin` 으로 두어 동작시키고 있다(개선 대상).

### 2.3 보고서 — 근태집계 (`/attendance-report`)

- **날짜 선택** — 하루를 골라 그날 기록만 본다(기본값: 오늘)
- **요약 카드 4개** — 출근 / 미출근 / 전체 체크 / 지오펜싱 준수
- **출근자 · 미출근자 명단** — 미출근자는 "활성 직원 중 그날 출근 기록이 없는 사람"으로 계산한다
- **CSV 다운로드** — 그날 상세 기록을 UTF-8 BOM CSV 로 내려받는다(엑셀에서 한글 안 깨짐)

## 3. 직원용 PWA (`employee-pwa/`)

메인 대시보드와 **분리된 별도 Vue 3 + Vite 프로젝트**다. 휴대폰 홈 화면에 설치해 쓴다.

| 화면 | 기능 |
|---|---|
| 출퇴근 (`/`) | 이메일·비밀번호 로그인 → GPS 취득 → 출근/퇴근 버튼. 당일 상태에 따라 버튼이 바뀐다 |
| 휴가 신청 (`/#/leave`) | 휴가 종류·기간·사유를 넣어 신청(상태는 `pending` 으로 생성) |
| 내 기록 (`/#/history`) | 본인 출퇴근 이력 조회 |

- 로그인한 계정(`auth.uid()`)으로 `employees.user_id` 를 찾아 **본인 직원 레코드**를 특정한다.
  → 계정과 직원이 연결되어 있지 않으면 아무것도 못 한다([9. 실운영 전 체크리스트](#9-실운영-전-체크리스트) 참고).
- GPS 는 `navigator.geolocation` 사용. **HTTPS 에서만 동작**한다.
- 라우터는 해시 방식(`/#/leave`)이라 하위 경로 배포에서도 새로고침 404 가 없다.

## 4. 지오펜싱 동작 방식

1. 앱이 휴대폰 GPS 좌표(위도·경도)를 얻는다.
2. `check_geofence(위도, 경도)` 함수가 활성 근무지 중 **가장 가까운 한 곳**을 찾아
   거리(m)와 반경 안에 있는지(`within`)를 돌려준다.
3. 출퇴근 기록에 좌표·근무지·거리·반경 내 여부가 함께 저장된다.

거리는 `haversine_distance()` 로 계산한다(지구를 구로 보는 대권거리, 반지름 6,371 km).
**반경 밖에서도 출퇴근 기록 자체는 막지 않는다.** 외근·현장 근무가 있기 때문이며,
대신 화면에 ⚠️ 영역 밖 + 거리로 표시되어 관리자가 판단한다.

## 5. DB 스키마

| 테이블 | 내용 | 주요 컬럼 |
|---|---|---|
| `employees` | 근태용 직원 명부 | `user_id`(auth 계정 연결) · `employee_code`(사번, UNIQUE) · `department` · `position` · `annual_leave_total/used` · `is_active` |
| `geofence_zones` | 근무지(지오펜싱 영역) | `name` · `latitude` · `longitude` · `radius_meters` · `is_active` |
| `attendance` | 출퇴근 기록 | `check_type`(`check_in`/`check_out`) · `latitude` · `longitude` · `geofence_zone_id` · `is_within_geofence` · `distance_meters` · `check_time` |
| `leave_requests` | 휴가·연차 신청 | `leave_type` · `start_date`~`end_date` · `days_count` · `status` · `approved_by` · `approved_at` |
| `overtime` | 초과근무 신청 | `overtime_date` · `start_time`~`end_time` · `hours` · `status` · `approved_by` · `approved_at` |

함수 2개 — `haversine_distance(lat1, lon1, lat2, lon2)`, `check_geofence(p_lat, p_lon)`.
스키마 원본: [`supabase/migrations/001_create_attendance_schema.sql`](../supabase/migrations/001_create_attendance_schema.sql)

> **`employees` 와 기존 `staff` 는 아직 별개 테이블이다.** 지금은 사번(`employee_code` = `staff.nik`)
> 으로만 맞춰 두었다. 통합할지 분리해 둘지는 결정이 필요하다.

### 임베드 주의

`leave_requests`·`overtime` 은 `employees` 로 향하는 외래키가 **2개**다(`employee_id`, `approved_by`).
PostgREST 조회 시 어느 쪽인지 힌트를 반드시 붙여야 하며, 빠뜨리면 HTTP 300(`PGRST201`) 이 난다.

```
employee:employees!leave_requests_employee_id_fkey(name,department)
approver:employees!leave_requests_approved_by_fkey(name)
```

## 6. 권한 (RLS)

5개 테이블 모두 RLS 활성, 모든 정책은 `TO authenticated`(익명 접근 차단).
역할은 `app_metadata.role` 만 본다.

| 대상 | 권한 |
|---|---|
| `super_admin` | 5개 테이블 전체 읽기·쓰기 (`admin_all`) |
| `staff` | 5개 테이블 **읽기만** (`staff_read`) — 조회는 되지만 승인·근무지 수정은 안 된다 |
| 일반 직원(PWA) | 본인 직원 레코드 조회, 활성 근무지 조회, **본인** 출퇴근·휴가·초과근무 조회 및 생성 |

직원은 자기 신청을 **만들 수는 있어도 수정·승인할 수는 없다**(UPDATE 정책 없음).
따라서 자기 휴가를 스스로 승인 처리하는 일은 구조적으로 불가능하다.

## 8. 배포

### 8.1 관리자 3개 화면

메인 대시보드에 포함되어 있어 별도 절차가 없다.

```bash
npm run build     # 타입·빌드 검증
npm run deploy    # GitHub Pages 반영
```

### 8.2 직원용 PWA — GitHub Pages 하위 경로 (게시 완료)

메인앱과 **같은 GitHub Pages 사이트의 하위 경로**에 얹는 방식(A안)으로 구성해 두었다.

| | URL |
|---|---|
| 메인 대시보드 | `https://hungaseo-arch.github.io/asuraDB/` |
| 직원용 PWA | `https://hungaseo-arch.github.io/asuraDB/pwa/` |

**적용된 설정** (이미 반영됨 — 다시 손댈 필요 없음)

| 파일 | 내용 |
|---|---|
| `employee-pwa/vite.config.ts` | `base: '/asuraDB/pwa/'` |
| `employee-pwa/public/manifest.json` | `"id"`·`"scope"` = `/asuraDB/pwa/`, `"start_url": "."`, 아이콘 상대경로, `any`+`maskable` |
| `employee-pwa/index.html` | `href="manifest.json"` (앞의 `/` 제거), `apple-touch-icon`, iOS 메타태그 |
| `employee-pwa/public/*.png` | `icon-192` · `icon-512` · `apple-touch-icon`(180px) 생성 완료 |
| `package.json` (루트) | `build:pwa` · `bundle:pwa` · `deploy` 스크립트 |

**배포 명령** — 목적에 따라 둘 중 하나를 쓴다.

```bash
npm run deploy:pwa    # PWA 만 /asuraDB/pwa/ 에 게시 (메인앱은 그대로 둠)  ← 권장
npm run deploy        # 메인앱 + PWA 를 한꺼번에 게시
```

`deploy:pwa` 는 `gh-pages --dest pwa` 로 **gh-pages 브랜치의 `pwa/` 디렉터리만** 교체한다.
루트의 메인앱 파일은 건드리지 않으므로, 작업 중인 미커밋 변경이 메인앱에 딸려 올라갈 걱정이 없다.

`deploy` 는 작업 트리 전체를 빌드해 올린다. **미커밋 작업이 있으면 그대로 공개되니**
메인앱까지 배포할 때는 커밋 상태를 먼저 확인한다.

**환경변수** — `employee-pwa/.env` 는 gitignore 대상이라 저장소에 없다. 빌드하는 컴퓨터마다
`.env.example` 을 복사해 만들어야 한다.

```bash
cp employee-pwa/.env.example employee-pwa/.env   # VITE_SB_URL, VITE_SB_KEY(anon 키)
```

**다른 선택지** (지금은 안 쓰지만 참고)

| 방식 | 특징 |
|---|---|
| B. Netlify / Vercel / Cloudflare Pages | 루트 배포라 `base` 수정 불필요, 환경변수를 UI 로 관리. 계정 연결 필요 |
| C. 별도 GitHub Pages 리포 | 메인앱과 배포 주기를 분리하고 싶을 때 |

> **HTTPS 필수** — GPS(`navigator.geolocation`)와 서비스워커는 보안 컨텍스트에서만 동작한다.
> GitHub Pages 는 HTTPS 라 문제없지만, 사내 HTTP 서버에 올리면 출퇴근 체크가 안 된다.
>
> **anon 키만 넣는다** — PWA 는 브라우저에서 도는 코드라 키가 그대로 노출된다.
> `service_role` 키를 넣으면 RLS 가 전부 무력화된다. 데이터 보호는 RLS + 사용자 JWT 로 한다.
>
> **게시 상태(2026-09-04)** — `https://hungaseo-arch.github.io/asuraDB/pwa/` 로 공개되어 있다.
> 다만 실제 직원 12명은 아직 `user_id` 가 비어 있어 **로그인할 수 없다.** 현재 로그인 가능한 것은
> 아래 테스트 계정 2개뿐이다. 직원 계정 연결은 9항 참고.
>
> | 직원 | Auth 계정 | 역할 | 용도 |
> |---|---|---|---|
> | `TEST-001` 테스트 계정 (jhseo) | `jhseo@ptascendo.com` | `super_admin` | 관리자 시점 — 전체 데이터 열람 |
> | `TEST-002` 테스트 계정 (gmail) | `hunga.seo@gmail.com` | `end_user` | 직원 시점 — 본인 데이터만 열람 |
>
> `end_user` 로 메인 대시보드에 접속하면 라우터 게이팅에 따라 `/quote` 로 간다(정상 동작).

- [ ] **직원 계정 생성 및 연결** — 직원마다 Supabase Auth 계정을 만들고
      `employees.user_id` 에 연결한다. 지금은 12명 전원 `NULL` 이라 **PWA 로 아무도 로그인해 쓸 수 없다**.

      역할이 비어 있으면 메인 대시보드에서 `/quote`(견적서 작성)로 들어갈 수 있으니,
